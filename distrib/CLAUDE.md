# librla/distrib

Multi-language distribution of librla (randomized low-rank factorizations: `orth_sketch`, `qr_sketch`, `svd_sketch`, `id_sketch`, `id_qrpiv`) with matching Python (`python/librla.py`, packaged via `python/pyproject.toml`), MATLAB/Octave (`matlab/librla.m`, a classdef with static methods) and Julia (`julia/src/LibRLA.jl`, packaged as `LibRLA` via `julia/Project.toml`) implementations.

## Layout, tests, demos

Each language directory has a `test/` (run `test_all`) and a `demo/` folder plus its own README.md. `compare/` has scripts comparing librla against SciPy and PyTorch, and `notes/` is an AI-generated, unverified knowledge base (read its README.md warning before trusting anything there).

## Experimental ports

`cpp/` (C++17 header-only), `rust/` (crate `librla`), `swift/` (SwiftPM `LibRLA`), `fortran03/` (Fortran 2003 `module librla`), `fortran95/` (Fortran 95 external subroutines `rla_d*`/`rla_z*`) and `fortran77/` (self-contained Fortran 77, same calls plus a work array) are experimental ports, version 0.1.0 each, tracking 1.2.1 semantics for real and complex double, dense and matrix-free. They differ from the three reference ports in three ways (Fortran 77: see below):

- All dense linear algebra goes through LAPACK/BLAS (`?geqp3`, `?orgqr`/`?ungqr`, `?gesdd`, `?gelsd`, `?trsm`, `?gemm`), with hand-written Fortran-symbol declarations. Accelerate is the default on macOS and binds its new LAPACK 3.11 interface (`<name>$NEWLAPACK` symbols, macOS 13.3+; each port has a legacy opt-out, and Fortran 95, which cannot bind them, always uses the legacy ones), which is up to 2x faster for complex BLAS than the legacy `<name>_` symbols; OpenBLAS and system LAPACK use the plain names.
- The random test matrix comes from LAPACK `dlarnv`/`zlarnv` (idist 2, uniform(-1,1)) driven by an `iseed(4)` RNG, and the default seed is the fixed `{0,0,0,1}` (deterministic, unlike Python's OS entropy).
- Every port's test suite prints the same five `CROSSPORT` lines (fixed Hilbert-type matrices, seed `{1,2,3,5}`). They match across ports and against `librla.py` fed the same `dlarnv` stream: integers exactly, floats to about 1e-11 relative (BLAS summation order).

C++/Rust/Swift use 0-based pivots and return `Vh`; Fortran 2003 and Fortran 95 use 1-based pivots and return `vh`/`vt`. When changing an algorithm, change the experimental ports too or note that they lag.

`fortran95/src/rla95_core.f90`, `librla95.f90`, `librla95_interfaces.f90` and `test/test_all.f90` are generated by `fortran95/tools/generate.py` from the templates in `fortran95/tools/` (real and complex halves); edit the templates or the script and run `make generate`, never the generated files (CI fails on stale ones via `--check`). Its Makefile builds with `-std=f95`, so no Fortran 2003 features (allocatable dummies, `move_alloc`, `[ ]` constructors, reallocation on assignment) can slip in.

`fortran77/` uses no LAPACK so that it can be compiled in any precision (`-freal-8-real-16 -fdefault-integer-8`; `make test-quad`): its own pivoted Householder QR (LAPACK `dlaqp2` algorithm), one-sided Jacobi SVD, and the `dlaruv` generator in integer arithmetic, which reproduces the `dlarnv` stream bit for bit, so its `CROSSPORT` integers match exactly and its floats to about 1e-11. Use only the double-precision specific intrinsics there (`dble`, `dcmplx`, `dconjg`, `dimag`): gfortran promotes them with `-freal-8-real-16`, but `cmplx` without a kind stays single precision. Its `src/librla77.f` and `test/test_all.f` are generated by `fortran77/tools/generate.py` (wrapping at column 72); its workspace layouts are fixed before the data-dependent run, so the `lw = -1` query is exact, and the test suite checks every routine with `lw` exactly the queried size.

## Contracts

- Two modes: `rtol < 1` is tolerance mode (adaptive rank); `rtol >= 1` is rank mode with `k = floor(rtol)`.
- Matrix-free operators (scipy `LinearOperator`, custom `LinearOperator.m`, and in Julia any operator with `size`/`eltype`/`adjoint`/`mul!`, e.g. LinearOperators.jl or LinearMaps.jl) support both modes, but there is a performance trap: in tolerance mode the deterministic fallback (`_get_matrix` / `get_matrix`, used when the sketch terminates early) may materialize the operator as a dense matrix, one matvec per column, at O(n) matvecs. Prefer rank mode for genuinely matrix-free operators.
- `extra_samples` (default 12) is the buffer beyond the target rank in both modes: rank mode samples `floor(rtol) + extra_samples` columns; tolerance mode accepts a sketch only when at least `extra_samples + 1` pivoted column norms fall at or below `rtol` times the largest. `extra_samples=0` selects the legacy last-column tolerance check.
- Other optional parameters (`block_size`, `power_iter`, `method`, `rng`) are documented in each function's header.

## API differences between languages

svd_sketch return convention (preserve it):

| Language | Returns | Reconstruction |
|----------|---------|----------------|
| Python | `U, s, Vh` | `A = U @ np.diag(s) @ Vh` |
| MATLAB | `U, s, V` | `A = U * diag(s) * V'` |
| Julia | `U, s, Vt` | `A = U * diagm(s) * Vt` |

Python and Julia return V transposed; MATLAB returns V (not transposed).

ID reconstruction identity for `id_sketch` / `id_qrpiv` (`k` skeleton columns, `T` is `k x (n-k)`):

```python
A[:, piv[k:]] = A[:, piv[:k]] @ T          # Python (0-based)
```
```matlab
A(:, piv(k+1:end)) = A(:, piv(1:k)) * T    % MATLAB (1-based)
```
```julia
A[:, piv[k+1:end]] = A[:, piv[1:k]] * T    # Julia (1-based)
```

## Cross-language consistency

When making changes:

1. Maintain API consistency across all three languages; change all three together.
2. Keep function signatures equivalent (accounting for language idioms).
3. Update tests in all three languages when adding features.
4. Ensure documentation stays synchronized in the per-language README.md files.
5. Preserve the svd_sketch return convention (Python/Julia: transposed V; MATLAB: non-transposed V).
